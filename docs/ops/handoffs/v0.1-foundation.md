### hashkit-match

**Status proposed:** `v0.5 — naive linear-scan matching ships for query()/query_all(); EmptySet + InvalidThreshold(>256) rejected; v1.0 ground-truth parity (1,000 hashes × 100 queries) green; MIH deferred to v2.0 hardening.`

**Branch:** `agent/wave-a-hashkit-match` (dedicated worktree off `main` @ `4e8622c`). Commit `8d23ae3`. Pushed to `origin/agent/wave-a-hashkit-match`.

**What landed** (all changes confined to `packages/hashkit-match/src/lib.rs`)
- `PdqMatcher::query` / `::query_all` implemented as a **naive linear scan** over the stored reference set (were `todo!()`). This is the correct, gating v0.5/v1.0 baseline. MIH (Multi-Index Hashing, Norouzi et al. 2012) is explicitly deferred to v2.0 — a performance hardening item, not a correctness requirement.
- `PdqMatcher` now stores the known-bad set in `Vec<PdqHash>` (replaced the unit placeholder); scans with `PdqHash::hamming`.
- `new()` now returns `MatchError::EmptySet` when the iterator yields zero hashes, in addition to the existing `InvalidThreshold(>256)` rejection. `with_default_threshold` inherits this (forwards to `new`).
- `query()` returns the closest reference within the threshold, else `None`; ties resolve to the earliest-inserted reference (deterministic).
- `query_all()` returns all references within the threshold, sorted ascending by distance (stable sort → insertion order preserved on ties).
- Added `len()`, `is_empty()`, `threshold()` accessors.
- Stayed on the crate's declared MSRV 1.75 (avoided `Option::is_none_or`, stabilised 1.82).

**Scaffold test changed (intentional):** the old `matcher_accepts_default_threshold` asserted an *empty* set is OK. That contradicts the new EmptySet contract, so it was replaced by `matcher_accepts_default_threshold_on_nonempty_set` plus explicit EmptySet tests. No loss of intent.

**Tests (9, all green)**
- `query_finds_known_near_hash` — near-hash recovery (perturb a reference by < threshold bits, get it back)
- `query_all_returns_all_within_threshold_sorted` — 3-of-50 within threshold, returned ordered by distance
- `query_returns_none_when_nothing_close`
- `matcher_rejects_empty_set` and `matcher_rejects_empty_set_via_default`
- `matcher_rejects_invalid_threshold` (>256) and `matcher_accepts_threshold_256` (boundary)
- `matcher_accepts_default_threshold_on_nonempty_set`
- `query_matches_ground_truth_linear_scan` — **v1.0 acceptance**: `query()` agrees with an independent hand-written linear scan over a 1,000-hash reference set across 100 random queries (mixed hit/miss population)

Synthetic random `[u8;32]` hashes via a fixed-seed SplitMix64 PRNG; **no** coupling to hashkit's pdqhash port.

**Gates (run from workspace root)**
- `cargo fmt --all -- --check` — clean
- `cargo clippy --workspace --all-targets -- -D warnings` — clean
- `cargo test -p hashkit-match` — 9/9 pass
- `cargo test --workspace` — green (hashkit's own 2 tests unaffected)

**Cross-track dependency (flagged, not blocking):** the naive matcher depends only on `hashkit::PdqHash::hamming`, which is already implemented — so this wave needed no real PDQ hash output and used synthetic hashes per the coordination boundary. The hashkit agent's real `hash_from_luma` port (`packages/hashkit`, still `todo!()`) is needed only later, for *realistic/integration* vectors exercising hashkit → hashkit-match end to end. No code coupling was introduced.
