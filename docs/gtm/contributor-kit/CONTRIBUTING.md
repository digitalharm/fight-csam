# Contributing to FightCSAM

Thank you for considering a contribution. FightCSAM (the developer brand for the
`digitalharm` packages) ships open, auditable, self-hostable building blocks that
help any online platform **detect, report, and prevent** CSAM. Because of what
this code touches, **credibility and restraint are the whole project.** A single
careless commit — a leaked credential, a real hash, an over-stated claim — does
more damage than a hundred good PRs do good. This guide is written so that one
good contribution is easy to make *and* easy to review, and so that the
dangerous surfaces are impossible to wander into by accident.

New here? Jump to:

- [The five rules you must honor](#the-five-rules-you-must-honor) — read these first, every time.
- [Where to report a security or abuse-sensitive issue](#reporting-security--abuse-sensitive-issues) — **never a public issue.**
- [Pick your first issue](#pick-your-first-issue) — the safe, well-scoped on-ramp.
- [Local setup per language](#local-setup-the-polyglot-monorepo) — Rust / Python / Go / TypeScript.
- [Running CI locally before you push](#running-ci-locally).
- [What we are *not* taking](#contributions-we-are-not-taking) — so you don't waste effort.

The longer policy lives in [`docs/safety-policy.md`](docs/safety-policy.md); the
governance invariants live in [`GOVERNANCE.md`](GOVERNANCE.md) (the rules no PR can
change). This file is the practical on-ramp.

## The five rules you must honor

These are **hard gates, not guidelines.** The safety guard CI
([`scripts/safety-check.sh`](scripts/safety-check.sh)) catches some of them
mechanically; all of them will get a PR closed. They are non-negotiable, including
in code generated by an AI assistant.

1. **Ship NO hash list, ever.** Real NCMEC, IWF, or Project Arachnid (Shield) hash
   data is credentialed and stays with the operator who holds the relationship.
   This repository contains **zero** known-CSAM hashes and never will. To test
   matching logic, use the deterministic synthetic fixtures in
   [`packages/detectkit-test`](packages/detectkit-test) — never a real list,
   never a "small sample," never an "anonymized" excerpt.

2. **Never commit real CSAM imagery or video. Ever. For any reason.** All test
   media is synthetic, non-harmful by construction, and reproducible from a
   documented seed/prompt (see `detectkit-test`). Opaque binary fixtures are not
   accepted. Every demo, example, Hugging Face Space, quickstart, and screenshot
   uses synthetic fixtures only.

3. **Never commit credentials or secrets.** NCMEC ESP tokens, IWF API keys,
   PhotoDNA keys, Project Arachnid Shield keys, AWS keys, signing keys — none of
   it. Use environment variables and document the *names* in an `.env.example`.
   Placeholder values in examples must read like placeholders
   (`NCMEC_API_KEY=your-key-here`, `<token>`, `example`, `dummy`).

4. **Never bypass the NCMEC / counsel gates.** Two tools have production paths that
   are deliberately fenced and must **stay** fenced until external owner gates are
   cleared:
   - **`cybertip-cli`** keeps real CyberTipline submission blocked
     (`ProductionSubmitBlocked`); only the dry-run / sandbox payload path is open.
     It does **not** open until an NCMEC ESP credential **and** outside-counsel
     sign-off **and** a consented filing partner all exist.
   - **`evidencevault`** keeps retention **unenforced** and KMS as a no-op until the
     same counsel sign-off lands.
   Do not "finish" these paths, remove the stubs, or wire a live endpoint "just to
   test." A PR that flips a gate will be closed regardless of code quality. If you
   want to *strengthen* a gate (more visible stub, better refusal message, more
   test coverage of the blocked path), that is very welcome — say so explicitly.

5. **Never claim "compliant."** Not in code, comments, READMEs, docs, the
   `/llms.txt` / manifest / Agent Skill surfaces, or anywhere else. These tools
   help an operator **take defensible, documented steps toward** their legal duty
   (UK OSA, EU DSA, US REPORT Act / TAKE IT DOWN Act / §2258A, AU eSafety); they do
   **not** make anyone compliant, and counsel is always required. Likewise: never
   claim we "beat" or "outperform" Meta / PDQ. Meta is **upstream and our
   conformance source**; `hashkit` *conforms* to PDQ and does not compete with it.
   Frame `hashkit`'s edge only as Rust/WASM portability + NCMEC conformance
   vectors. Pair every legal-duty statement with the counsel disclaimer and the
   "known-hash matching alone is not enough" framing.

If you are ever unsure whether something is safe to commit, **stop and ask in a
[private channel](#reporting-security--abuse-sensitive-issues) first.** Defaulting
to private is always the right call here.

## Reporting security & abuse-sensitive issues

**Do not open a public GitHub issue for anything in this list.** Public disclosure
of these can cause real-world harm or hand an adversary a roadmap.

Email **`security@digitalharm.org`** (see [`SECURITY.md`](.github/SECURITY.md)) for:

- A vulnerability or bypass in the safety guard (`scripts/safety-check.sh`).
- Hash drift between language bindings of `hashkit` (a false-negative vector).
- Authn/authz flaws in `hashstream`, `cybertip-cli`, or `evidencevault`.
- Cryptographic issues in `c2pa-lite` or in snapshot signing.
- **Anything that could cause real CSAM to be mishandled, stored, exposed, or
  missed** — including a detection-bypass technique.
- Any case where you believe real CSAM or a real hash list has been committed to
  this repo or a fork. Report it privately and immediately; do not quote, attach,
  or screenshot the material.

If you have encountered actual CSAM anywhere (not a repo issue, a real-world
sighting), it must go to the proper authority — in the US, the
[NCMEC CyberTipline](https://report.cybertip.org/) — not to this project.

We confirm receipt within 5 business days and follow Coordinated Vulnerability
Disclosure. Conduct concerns go to **`conduct@digitalharm.org`**
(see [`CODE_OF_CONDUCT.md`](.github/CODE_OF_CONDUCT.md)).

## Pick your first issue

The fastest, safest way in is a **credential-free** contribution — work that
cannot touch a real list, real imagery, a credential, or a gated path. We curate
these and label them so you can find them:

- [`good-first-issue`](https://github.com/digitalharm/fight-csam/labels/good-first-issue)
  — small, scoped, with an acceptance test and a "why this is safe to work on" note.
- [`help-wanted`](https://github.com/digitalharm/fight-csam/labels/help-wanted)
  — larger but still safe-by-construction.
- The pinned **conformance-reproduction** tracking issue — reproduce `hashkit`'s
  PDQ output byte-for-byte on your OS/arch using synthetic vectors only. This is
  the single best first issue in the project: it is safe by construction, it is
  high-status (you get credited by name), and it directly satisfies a roadmap Beta
  gate (independent reproduction by an external contributor).

See [`docs/gtm/contributor-funnel.md`](docs/gtm/contributor-funnel.md) for the
full label taxonomy and a worked list of starter issues. **The safe surfaces are
wide open; the gated surfaces are fenced — by design.**

Before you start non-trivial work, please claim the issue (comment) so we don't
duplicate effort, and open an issue first for any design-level change (see
[PR process](#pr-process)).

## Local setup (the polyglot monorepo)

This is a polyglot monorepo: **Rust + WebAssembly, Python, Go, and TypeScript**,
each package self-contained under [`packages/`](packages). There is no single
build system — the root [`Makefile`](Makefile) delegates to each toolchain, and
each package's `README.md` documents its native build. Set up only the
language(s) your change touches.

### One-time, repo-wide

```bash
git clone https://github.com/digitalharm/fight-csam.git
cd fight-csam
make list          # show all 11 packages
make status        # show each package's STATUS (Planned / In Progress / ...)
make safety-check  # run the SCOPE/SAFETY guard against your last commit
```

Optional but recommended — wire the safety guard as a pre-commit hook so you can
never push a violation:

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/usr/bin/env bash
exec bash scripts/safety-check.sh --staged
EOF
chmod +x .git/hooks/pre-commit
```

### Rust — `hashkit`, `hashkit-match`, `c2pa-lite`, `safemod`

A single Cargo workspace at the repo root (see [`Cargo.toml`](Cargo.toml)).
Toolchain: stable Rust with `rustfmt` + `clippy`.

```bash
rustup component add rustfmt clippy
cargo build --workspace
cargo test  --workspace --all-features
cargo fmt   --all -- --check          # CI runs this
cargo clippy --workspace --all-targets -- -D warnings   # warnings fail CI
```

`hashkit` also targets WASM (`wasm` feature, built with `wasm-pack`); the WASM
build must produce byte-identical hashes to the native build on the same corpus.
Tests live in-line under `#[cfg(test)]` in each crate's `src/`; conformance
vectors live in `packages/hashkit/vectors/`.

### Python — `detectkit-test`, `promptshield`, `trainguard`, `csam-shield` (python), `cybertip-cli` (python)

Python 3.12 in CI (3.10+ supported). Each package is an editable install with a
`[dev]` extra; lint is Ruff.

```bash
cd packages/promptshield            # or any Python package; csam-shield/python, cybertip-cli/python
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
ruff check src                       # CI runs this
pytest -q                            # tests live in ./tests/
```

### Go — `hashstream`, `evidencevault`

Go 1.22. Each Go module is **independent** — there is no root `go.mod`. The module
path is `github.com/digitalharm/fight-csam/packages/<name>`, which is why Go
releases use **per-module** tags (`packages/hashstream/v0.1.0`), never a bare
`v0.1.0`.

```bash
cd packages/hashstream               # or packages/evidencevault
go build ./...
go vet   ./...                       # CI runs this
go test  ./...                       # *_test.go alongside sources
```

`hashstream` also ships a TypeScript client SDK at `packages/hashstream/sdk-ts`
(see the Node section).

### TypeScript / Node — `csam-shield` (node), `cybertip-cli` (node), `hashstream/sdk-ts`

Node 20. Tests are co-located `*.test.ts`, compiled by `tsc` to
`dist/**/*.test.js`, and run with the built-in Node test runner.

```bash
cd packages/csam-shield/node         # or cybertip-cli/node, or hashstream/sdk-ts
npm install --no-audit --no-fund
npx tsc --noEmit                     # typecheck (CI runs this)
npx tsc                              # build
node --test dist/**/*.test.js        # run tests
```

> Tip: a change rarely needs all four toolchains. Set up only what your PR
> touches; CI will exercise the full matrix.

## Running CI locally

CI is four matrices (see [`.github/workflows/ci.yml`](.github/workflows/ci.yml))
plus the safety guard ([`.github/workflows/safety-guard.yml`](.github/workflows/safety-guard.yml)).
Reproduce the relevant ones before you push:

| What CI checks | Run locally |
|---|---|
| **Safety guard** (every PR) | `make safety-check` (or `bash scripts/safety-check.sh --staged`) |
| Rust workspace | `cargo fmt --all -- --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace --all-features` |
| Go (`hashstream`, `evidencevault`) | `cd packages/<pkg> && go build ./... && go vet ./... && go test ./...` |
| Python (×5) | `cd packages/<pkg> && ruff check src && pytest -q` |
| Node (×3) | `cd packages/<pkg> && npx tsc --noEmit && npx tsc && node --test dist/**/*.test.js` |
| Everything that has tests | `make test` (best-effort; delegates to each package) |

**The safety guard must pass.** If it flags a genuine false positive, do **not**
work around it silently — explain the reasoning in your PR description and tag the
maintainers. Network-dependent tests must be gated behind an env var and skipped
in default CI; CI runs offline.

## PR process

1. **For anything beyond a small fix, open an issue first.** Bug → bug report;
   new behavior or an API/scope change → feature/design proposal; a hash mismatch
   → conformance-discrepancy. The per-package `README.md` is the design contract;
   substantive changes need alignment before code. (Security/abuse-sensitive items
   skip this and go to the [private channel](#reporting-security--abuse-sensitive-issues).)
2. **Branch** off `main`. Keep the PR focused on one concern.
3. **Add or update tests** in the package's test location (above). A bug fix needs
   a regression test; new behavior needs coverage. Use synthetic fixtures only.
4. **Run the relevant CI locally**, including `make safety-check`.
5. **Open the PR** and fill in the [pull request template](.github/PULL_REQUEST_TEMPLATE.md)
   — including the safety checklist (the "no hash lists / credentialed data / real
   imagery added" boxes and the "did not touch a gated path" attestation). PRs that
   leave the safety checklist blank will be asked to complete it before review.
6. **Status changes** (e.g. In Progress → Alpha) update both
   [`docs/roadmap.md`](docs/roadmap.md) **and** the package's `STATUS` file in the
   same PR, with evidence the acceptance criteria are met.

Single-writer surfaces: `csam-shield`'s core orchestration and `create-fightcsam`
are maintainer-led because of blast radius — coordinate in an issue before sending
a large PR to those. Thin connector/adapter packages are great places for a first
real feature.

### Commit & code style

- Per-language formatters are authoritative: Rust `rustfmt`; Python Ruff (+ Black
  conventions); Go `gofmt`; TypeScript via the package's `tsc`/Biome config.
- Commit messages: imperative mood ("add MIH lookup", "fix hash drift on
  big-endian"), reference the issue, keep them honest. **No emojis** in commit
  messages.
- Synthetic fixtures must be reproducible from documented seeds/prompts, not
  opaque binaries.

## Recognition

This is a solo, self-funded project, and contribution is how it earns a future.
We take credit seriously:

- Every merged contributor is listed in `CONTRIBUTORS.md`.
- Each release's notes carry a "thanks to" line naming that release's contributors.
- **Conformance reproducers are credited by name** — reproducing `hashkit`'s PDQ
  output on a new OS/arch is a roadmap-gating contribution, and we treat it that way.
- The strongest, most safety-aware early contributors (typically from the
  conformance or connector work) are invited to become **named co-maintainers** —
  fixing the bus-factor is an explicit project goal.

The gated legal tier (`cybertip-cli` / `evidencevault` production paths) stays
**maintainer- and counsel-controlled**; that is a deliberate fence, not a snub.
There is plenty of high-impact, fully-credited work everywhere else.

## Contributions we are NOT taking

To save you effort, these are out of scope. The portfolio is intentionally bounded
at 11 tools, and some surfaces are fenced for safety/legal reasons.

- **A bundled hash list, or any real CSAM hash/imagery** — the core invariant; the
  operator always brings their own credentialed list. (See rule 1–2.)
- **Wiring `cybertip-cli` to real CyberTipline submission, or `evidencevault` to
  enforced retention / live KMS** — these are NCMEC-ESP- and counsel-gated and stay
  stubbed until those owner gates clear. (See rule 4.) Strengthening the stubs is
  welcome; bypassing them is not.
- **New top-level tools / packages** — the 11 are deliberate. Pitch the idea in a
  Discussion; expect a high bar.
- **A general-purpose rules engine, case-management system, PII detector, or
  toxicity/abuse classifier** — these are out of scope and well-served upstream
  (e.g. ROOST's Osprey rules engine + Coop console, Microsoft Presidio for PII).
  We *wrap and credit* such tools; we do not reimplement them.
- **Anything framed as "compliance attestation," "turnkey compliance," or
  "beats Meta/PDQ"** — see rule 5.
- **Real-credentialed integration tests in default CI** — must be env-gated and
  skipped offline.

When in doubt, open an issue and ask before you build. Thank you for helping make
CSAM-safety infrastructure something every platform can reach for.
